# Roadmap

What is built, what is wrong, and what comes next, ordered by impact. Every item has a way to check it worked.
Status: `[x]` done, `[ ]` planned.

## Plan: NPU decodes, the RTX 3050 reads and remembers (agreed Oct 2026)
Measured on this machine: 5.8 GB of the 6 GB VRAM are free (the desktop runs on the iGPU), fp16 matmul 11.5 TFLOPS (~10-20x the NPU's 93 tok/s prompt reading), a CPU->GPU->CPU round trip of a decode-sized vector costs ~20 us, host->GPU copies run at 12.5 GB/s, and GPU attention for one decode token at 16k context costs ~15 ms for all layers (the numpy path scales to hundreds of ms).
Roles: **NPU = decode matvec of every layer (the weight stream, the bottleneck)**; **GPU = prompt reading (prefill), KV cache and attention, linear-attention state, embeddings**; CPU = glue.
Target: three usable models: **fast** (Qwen3-0.6B, then Qwen3.5-0.8B), **medium** (Qwen3-1.7B, then Qwen3.5-2B), **slow and high quality** (Qwen3.5-4B).
- [x] **Phase 1 (done, profile "Assisted" only; "NPU only" keeps the old all-NPU path)**: `src/gpu_qwen.py`. Qwen3-1.7B measured: prompt reading **93 -> 1333 tok/s (512 tokens), 2582 (2048), 2467 (6000)**; decode **110 / 113 / 115 ms per token at 0 / 1500 / 6000 tokens of context** (was 150 / 187 / ~290 with CPU attention); max context 8192 with a bf16 KV cache in VRAM (VRAM use 4.4 GB: 3.4 GB weights for prompt reading + KV); RAM free +4 GB (no bf16 prompt copy, no CPU KV). Logits match the NPU prompt reader (cosine 0.99986). 5 of 8 benchmark answers identical, 3 diverge mid-text from bf16 rounding and stay correct. The NPU still generates every token (94 of 110 ms per token). Server test passes in both profiles (`tests/test_server.py`).
- [x] **GPU memory cap and context window are settings** (Setup tab, Assisted profile; `llm_vram_gb` default 5.5, `context_tokens` default 8192; applied at the next Load). The window is cut to what fits after the weights (`GpuCore` computes it) and the model state shows the real size; if even 2048 tokens do not fit the model loads NPU-only. Measured with Qwen3-0.6B: asking for 120k in 5.5 GB gives 32.9k. NPU-only keeps 4096 (float32 KV in RAM). Dense Qwen3 costs 114 KB of KV per token (16k = 1.9 GB bf16), so 60k-120k only becomes realistic with Qwen3.5 (~12 KB per token: 120k = 1.5 GB) or an int8 KV cache plus streamed weights.
- [x] **Model line-up (one loaded at a time, switched with Unload/Load as today):** fast = Qwen3-0.6B (-> Qwen3.5-0.8B), medium = Qwen3-1.7B (-> Qwen3.5-2B, the long-context one), slow and high quality = Qwen3-4B (already supported by the engine except that its 8 GB of bf16 weights need layer streaming for GPU prompt reading) (-> Qwen3.5-4B). **Done:** fast Qwen3.5-0.8B, medium Qwen3.5-2B, slow Qwen3.5-4B (Assisted); Qwen3-1.7B / 0.6B stay for NPU only.
- [x] **Phase 3 for the 2B (done): Qwen3.5-2B runs with the NPU generating and the GPU doing DeltaNet, attention and prompt reading** (`src/gpu_qwen35.py`, `src/qwen35_npu.py`). Checked against the Hugging Face reference: logits cosine **0.9999**, same top-5; stepwise decode vs prefill cosine 0.99988; snapshot/rewind of the recurrent state works. Measured (4 GB VRAM limit): context window **58.8k tokens**, load 32 s; prompt reading **1700 tok/s at 6k, 1800 at 17k, 1500 at 41k**; decode **8.0 / 8.2 / 7.9 tok/s at 6k / 17k / 41k tokens**; a hidden key found in the text at 5.8k, 17k and 41k tokens. With a 5.5 GB limit and a 130k window: **101k tokens read in 91 s (1112 tok/s), decode 7.8 tok/s, key found** (VRAM at the edge; the window formula now reserves attention scratch that grows with the window). The 8-prompt benchmark: 8.07 tok/s, coherent answers (knows paru is an AUR helper, which Qwen3-1.7B did not).
- [x] **Phase 3, Qwen3.5 port** (Gated DeltaNet + gated attention + partial RoPE; the recurrence and its state live on the GPU in torch, which is far easier than numpy): 0.8B, 2B, then 4B. **Done for 0.8B, 2B and 4B.**
- [x] **Phase 4, the 4B profile**: weights that do not fit in VRAM are streamed layer by layer from RAM at 12.5 GB/s for prefill (4.2 GB int8 = ~0.35 s per pass). **Done differently:** the GPU keeps the 4B in int8 (with the same quantisation as the NPU), no layer streaming needed.
- [~] **Phase 5, set defaults**: the fast / medium / slow selector is done; still open: router classifier on by default (Qwen3.5 as judge, re-measure) and the reranker on the GPU.

## Open questions for the next session (Oct 2026, branch `perf/medicion`)
- **NPU-only attention** (head-major KV cache, no float64 copy per layer): Qwen3-0.6B decode per token at 256 / 1024 / 3500 tokens of context went 99 / 290 / 1056 ms -> 59 / 83 / 167 ms (`bench/attn_vs_ctx.py`). `tests/test_server.py` passes (19 PASS). Still to confirm: identical tokens (`bench/token_equiv.py`) and the same on Qwen3-1.7B. Only matters for the NPU-only profile (4096-token window); the Assisted profile already attends on the GPU.
- **Why the 4B holds only ~6k tokens with 5 GB of VRAM: measured with `bench/vram_ctx.py` (GPU free, 28 MiB in use), Qwen3.5-4B, int8 layers 3.65 GB, 32,768 bytes of KV per token:** budget 4 GB -> does not fit (0 tokens); **5 GB -> 19,889 tokens**; **5.5 GB -> 33,643 tokens**. **Explained:** the saved settings (`~/.config/npu-lab/rules.json`) have `llm_vram_gb: 4.5`, not 5, and the table grows ~27.5k tokens per GB, so 4.5 GB gives ~6.1k tokens (19,889 - 13,754), the number seen in use. It is the setting, not the engine: raising it to 5.0 gives ~20k and 5.5 gives ~33k. The same file has `gpu_share: 0.5`, and the share's output-head rows (`lm_tail`, ~0.3 GB for the 4B) are allocated after the window is computed, so they are not counted in the budget: leave ~0.3 GB of the 6 GB card free when the share is on. The budget is a cap on this process, not a reservation: other programs on the GPU can still make a load fail. To check once on the server: set 5.5, Load the 4B, compare the window in the model state and `nvidia-smi` with this table.
- Prefill cause on NPU-only (187 tok/s at 256 tokens -> 141 at 2048), cost of changing instruction buffers (~410 us is quoted, never measured), and whether `--fuse-proj` is needed at all (qkv and gate|up are already concatenated in decode).

## Optimization backlog (Oct 2026): squeezing NPU, GPU and CPU
Where one decoded token goes today (Qwen3.5-2B, ~125 ms): ~90 ms the NPU streaming 1.9 GB of int8 weights (~21 GB/s), ~170 NPU calls per token (~120 us fixed each, ~20 ms), GPU conv/recurrence/attention steps with a ~20 us round trip per layer, numpy glue on the CPU (norms, SiLU, concatenations). The NPU kernel is within ~1.5x of its int16 multiply-accumulate floor, so more bytes per second will not come from the NPU alone.
Ranked by expected gain per effort (estimates, not measurements, except where marked):
1. [x] **Profile one token (done, Qwen3.5-2B, 112 ms)**: NPU calls 95 ms (85%; `pyxrt.wait` 86 ms = the weight stream, host Python 8 ms), GPU DeltaNet 9.3 ms, GPU attention 3.8 ms, CPU glue 3.5 ms. Mapped (zero-copy) NPU buffers saved ~1 ms: the NPU is bandwidth-bound, not host-bound.
2. [x] **GPU share of the decode matvecs (done; setting 0 / 25 / 50 %, default 0 = NPU only; Qwen3.5 only).** Every layer matrix and the output head are split by rows: the NPU runs the first rows, the GPU the last rows from the weights it already holds for prompt reading, on a side stream while the NPU streams (each GPU part is one CUDA-graph launch). Results are the same tokens (logits cosine 0.9999). Qwen3.5-2B, ms per token / tok/s: **0%: 112 / 8.9, 25%: 96 / 10.4, 50%: 73 / 13.8 (+55%)**. NPU kernels with fewer rows must be built per share level (`scripts/build_matvec.py --shared4 $(python src/qwen35_npu.py --model DIR --shapes --share 0.5)`; the System check prints the command). Original idea text: The GPU already holds every layer weight in VRAM for prompt reading; its memory moves ~190 GB/s (9x the NPU). Splitting each matrix by rows so both stream at the same time gives ~+25% decode at a 30% GPU share and ~2x at 60%. The honest consequence: the pure-speed optimum is GPU-heavy; the NPU stays central for power and for keeping the GPU free. Default stays 0%, the user picks the share.
3. [ ] **Smaller output head** (`NPU_FAST_VOCAB`): the 248k-token head is 27% of the bytes of the 2B (509 MB per token); a 40k subset gives ~+20% decode; make it default only after the quality check is repeated on Qwen3.5.
4. [x] **CUDA graphs for the GPU steps (DeltaNet done: 9.3 -> 3.9 ms per token; attention steps still eager because the key length changes every token)**; open: **fused kernels** (~15 small launches per DeltaNet layer today): ~-10 ms per token. Also try `flash-linear-attention` kernels for the DeltaNet prompt scan (the Python chunk loop dominates long prompts).
5. [~] **Cut the fixed cost of NPU calls and CPU glue** (mapped buffers done; in-place numpy for norm/SiLU/residual still open): preallocated buffers and mapped (zero-copy) BOs, fewer syncs, in-place numpy for norm/SiLU/residual; ~-8 to -12 ms per token.
6. [x] **Persist document state to disk**: after reading a long document, save the KV cache of the full-attention layers plus the DeltaNet snapshots keyed by content hash (100k tokens = ~1.2 GB for the 2B). Re-opening it costs about a second instead of 90 s. The biggest win for the large-documents/code use case. **Done (`src/statecache.py`, setting "Document cache on disk", default 8 GB, least-recently-used eviction):** a 28,977-token document took 17.9 s to read the first time and 1.1 s from the cache in a freshly loaded engine (16x), ~360 MB per cached position; a second question about the same document in the same session read in 0.7 s.
7. [ ] **Speculative decoding with the model's own MTP head** (Qwen3.5 ships one extra layer for this): the batched-vector kernel measured NV=2 at 1.25x the cost of one token, so ~1.3-1.4x with typical acceptance. Medium effort.
8. [ ] **Batching independent requests** (document map-reduce, conversation compaction, router): the 4-vector kernel measured 1.7x cheaper per vector, so summarising several chunks at once is nearly free throughput (not lower latency for one chat).
9. [ ] **KV cache in fp8/int8** for the full-attention layers (doubles the window per GB) and attention sinks / token eviction when even that is not enough.
10. [ ] Prompt reading is already 1100-1800 tok/s; progress reporting and chunked cancel for very long prompts.

## 1. Field report: what goes wrong today
Taken from real use of the chat with "local docs" and "web search" both ticked.

| Question | What happened | Cause |
|---|---|---|
| "how do I make a class in TypeScript" | answered with `typst` commands | docs retrieval matched *typescript* to *typst*; the CLI-docs index should not even be consulted for a programming-language question |
| "what happened on <date> in <country>" | useful, current answer from web sources | worked: this is what web search is for (cannot be verified offline, read the cited links) |
| same question | also cited `man:amidi`, `tldr:es/cal`, `man:eventlogadm` | the top-4 excerpts are always injected, **even when none is relevant** |
| "what did we talk about in this chat" | searched the web for "chat", answered about ChatGPT | a question about the conversation must be answered from the history, with no retrieval |
| any | `web:duckduckgo.com` listed as a source | search-engine pages are not filtered out of the results |
| "how to make homemade soap, ingredients only" (Spanish) | degenerate loop: repeated "Aceite de coco / oliva / girasol / almendras: 100 ml" until the token limit, never closing the list | no repetition penalty / loop guard in decoding; small model on a list-style answer. TODO: add `repetition_penalty` (~1.1) or no-repeat n-gram, and stop generation when the same line repeats 3+ times; add this prompt to the eval set (section 6) |
| any | code fences sometimes show on one line | fences that start mid-line are not recognised by the Markdown renderer |

Root problem: **retrieval is switched on by checkboxes, not decided per question**, and nothing checks whether what was retrieved is any good.

## 2. P0: decide per question, and drop junk (small, big payoff)
Goal: the right source for each question, and no source at all when nothing relevant exists.
- [x] **Auto mode** for docs and web (Auto / On / Off per source, default Auto). The checkboxes stop being "always inject".
- [x] **Relevance gate** for docs: inject an excerpt only if its score passes a threshold or the command name appears in the question as a whole word; otherwise say nothing instead of guessing. Threshold is a setting.
- [x] **History-only questions** ("what did we talk about", "summarise the above", "and in Python?", "repeat that") skip retrieval entirely.
- [x] **Filter web results**: drop search-engine and aggregator pages, duplicates by domain, results with no readable text.
- [x] **Query rewriting**: build a standalone search query from the question plus recent turns instead of sending the raw prompt.
- [x] Tolerant Markdown fences (``` starting mid-line, missing newline before the closing fence).
- Check: the field-report table becomes a regression test (section 6) and every row passes.

## 3. P1: a router with criteria you control
Goal: the model (plus simple rules) decides *whether* to look something up, and you can edit the criteria.
- [x] **Rule layer first** (fast, predictable), driven by a user-editable file (`~/.config/npu-lab/routing.json`, also editable in Settings):
  - time-sensitive words (today, yesterday, latest, price, version, news, years >= current year, "who is the current...") -> **web**
  - the question names an installed command/tool, or asks "how do I <do X> in the terminal" -> **docs**
  - references to the conversation ("above", "you said", "we talked") -> **history**
  - general programming / concepts -> **none** (answer directly; web optional)
- [x] **Model classifier second** (built; **with the 3B it reaches 92%** as fallback after the rules (83% alone, 79% rules only) but takes ~40 s per question while the 3B reads prompts token by token; with the 1.5B it was 83%/46%. Still **off by default**; worth enabling once a model that reads prompts fast is good enough. Earlier note on the 1.5B: measured 46% alone, 83% as fallback vs 79% for rules; below the 90% target, see `tests/eval_classifier.py`; a better prompt or a bigger model may change this) for what rules cannot tell: the local model gets the criteria and a few examples and answers one word
  (`NONE | DOCS | WEB | HISTORY`) with a tiny token limit. Measure its accuracy against the rules before trusting it.
- [x] **Always show the decision** in the UI ("used: web (time-sensitive)") with a one-click override ("answer without searching" / "search anyway").
- [x] **Escalation hint** (long or multi-part questions; needs a cloud provider): when the model is unsure or the question is long/complex, suggest "ask the cloud" (a button, never automatic).
- Check: >= 90% agreement with hand-labelled routing on the evaluation set; no regressions in answer quality. Rules: 19/24 on the classifier set (the rule words were tuned after seeing it, so treat as optimistic); the misses are general questions that default to docs, which the relevance gate keeps harmless.

### 3b. Model mixer: pick the model by difficulty (idea, not built)
Goal: answer easy questions with the fast model and send hard ones (long code edits, multi-step reasoning) to the slow high-quality one, without the user choosing each time. A deciding component, not a generating one: it only outputs a label (`fast | medium | slow`), the way the source router already outputs `none | docs | web | history`.
- **What is measured today that bounds the design:** one model is loaded at a time (a switch is Unload + Load: 0.8B ~4 s, 2B ~7 s, 4B ~40 s on this machine), decode 15 / 8.9 / 4.1 tok/s for 0.8B / 2B / 4B, and in the long-chat test only the 4B edited code correctly while the 0.8B and 2B kept the facts but not the edits. So the mixer's real job is "does this need the 4B?", and the cost of being wrong is a 40 s model switch, which means it should decide **per conversation or per task, not per message**.
- **Orchestrator options, cheapest first** (none of them needs a big model resident):
  1. Rules, as `src/router.py` does today (words such as "refactor", "write a function", file names, long pasted code, a question length) -> label. Zero memory.
  2. A small classifier on the embedding the search already computes (MiniLM, a few MB, milliseconds on the GPU or CPU): logistic regression trained on a labelled list of prompts. Needs ~100-200 labelled prompts and a held-out check; no NPU.
  3. The loaded small model as judge (`engine.classify`, exists, off by default): measured on Qwen3-1.7B 83% alone and 92-100% after the rules, but it costs a model call per question.
- **Suggest, do not switch silently:** like the "ask the cloud" hint, show "this looks like a code edit: switch to the 4B (about 40 s)?" with a button. Automatic switching only inside a task the user started (for example the terminal agent), and always shown.
- **Can the machine hold two models at once?** [pending, measure first] Memory budget: VRAM ~0.9 GB (0.8B) or ~3.65 GB (4B int8) of weights plus KV, RAM 16 GB shared with the iGPU; on the NPU the roadmap says two 4-column contexts can coexist but this was never tried with two different models. The orchestrator itself (rules or MiniLM) fits anywhere; the open question is only whether a fast and a slow model can be resident together to avoid the 40 s switch. If not, keep one resident and switch on demand.
- **Check:** on a labelled set of ~50 prompts (easy, medium, needs-the-4B) the label agrees >= 85% with the hand label, a wrong "fast" on a hard task is rarer than a wrong "slow" on an easy one (the first costs quality, the second only time), and the router adds < 50 ms.

## 4. P1: memory and context
Goal: remember more without getting slower or running out of window.
- [x] **Reuse the KV cache across turns** (prefix caching): today every turn re-reads the whole history. (done)
- [x] **Rolling summary**: when the window fills, summarise the oldest turns instead of dropping them. **Done:** when the conversation passes a share of the window (default 70%, editable) the model summarises the old turns into notes and keeps the last 3 verbatim (`compact` in `src/serve.py`).
- [ ] **Compaction: make it cheaper and make it keep what matters** (measured Oct 2026 with `tests/eval_long_chat.py`, Assisted profile, window 2048, 48 turns). Qwen3.5-0.8B: the compaction at turn 30 stalled that turn for **29.5 s** (a normal turn is 1-2 s; the cost is the model writing the ~400-token notes at 15 tok/s, plus re-reading the 278-token prompt from scratch), and afterwards it **forgot the facts planted at turn 1** (project name, port, cat: it answered "ProjectName", port 8080). **Qwen3.5-2B (same test, 2 compactions): remembers everything** (its notes keep `Project: Nebula, Port: 8431, Cat: Zeta` as a list and survive the second compaction), so quality is a matter of model size; but the stalls are far worse: **78 s and 93 s** (turns 25 and 40; median turn ~2-3 s, i.e. ~30x), because it writes ~400 tokens at 8.9 tok/s and the second compaction summarises the previous notes plus the new turns again. **Qwen3.5-4B (34 turns, 1 compaction): the stall is 98 s** (turn 26, 4.1 tok/s), and the notes **changed the port from 8431 to 8432** (`Project: Nebula (port 8432)`), so it answered 8432: a summary can corrupt a number, not only drop it; the code checks (executed, not word-matched) all passed and late turns were 1.38x the early ones. Together: forgetting is a small-model problem (0.8B), number corruption happens even at 4B, and the stall grows with the model (30 s, 78-93 s, 98 s). This is why idea 4 (keep names, numbers and ports verbatim outside the summary) is needed on top of the cheaper compaction. The cost grows with the model, which makes ideas 2 and 3 below the priority: the blocking compaction is the part users will notice, not the forgetting. Ideas, by expected gain:
  1. **Facts survive compaction by construction**: whatever the user marks as "remember this" lives in the system prompt (Remembered facts), which compaction never touches. Offer "remember this" on a message in the UI instead of hoping the summary keeps it.
  2. [x] **(done, `serve.py` + `web/index.html`)** **Compact in the background, after an answer, not before the next question**: the user is reading the answer anyway, so the 30 s is hidden. Apply the notes at the start of the next turn; if the user asks first, fall back to today's blocking path.
  - Result of 2 (Qwen3.5-2B, 48 turns): the answer now arrives in 1.9 s and 3.1 s on the two compaction turns (before: 78 s and 93 s before any answer); the 71-73 s of summarising happen afterwards on the same stream and the page lets you type meanwhile (if you send before the notes arrive, it waits for the rest and says "tidying up"). The GPU/NPU stays busy during those 71 s, so a question asked right away still waits: idea 3 is what shortens it. Found on the way: the compaction progress messages carried `done: <n>` and the page read that as the end of the answer (a bug that predates this work: it threw a TypeError when summarising in 2 or more pieces); they now carry `step`, and the page requires `done === true`. The 2B passed the three memory checks but failed the executed code-edit checks in this run (its edited `slugify` does not work), which the older word-matching check had hidden.
  3. [x] **Rolling, incremental notes** (done, `compact()` in `src/serve.py`; `tests/test_compact.py` offline with a fake model). Measured on Qwen3.5-2B, 48 turns, 2 compactions: the summarising that follows an answer went from **71-73 s to 21 s and 29 s**, answers still arrive in 1.9 s on the compaction turn, the three memory checks pass, late turns are 0.48x the early ones (the notes keep the window small). Notes are 250 tokens (150 words) and start from the previous notes. The 2B still fails the executed code-edit checks (model capacity). **Qwen3.5-4B (34 turns, 1 compaction): all 6 checks pass** (port stays 8431, executed `slugify` edit works), the summarising after the answer took **39 s (was a 98 s stall before the answer)**, late turns 1.15x the early ones. Fixed on the way: the pinned lines of a second compaction also picked the model's summary bullets of the first one (they contain digits); now only the pinned block of earlier notes counts.
  (original idea): when the conversation passes ~50% of the window, summarise only the turns that just aged out together with the previous notes (the current code summarises all the old turns at once), with a lower notes budget (~200 tokens). Less to write per compaction and the stall disappears.
  4. [x] **Pin the entities before summarising** (`src/pins.py`, used by `compact()`): the user's own lines that carry a number, port, path, file name or "called X" (max 12 lines of 220 characters, newest win) are copied word for word at the top of the notes, so a summary cannot drop or change them. Checked: `tests/test_pins.py` (offline) and `tests/eval_long_chat.py` on the 0.8B, which now **passes the three memory checks** after the compaction (before: forgot all three). Still open: the stall (30 s on 0.8B), and the 0.8B's own summary is a transcript copy, not notes; the 0.8B also fails the code-edit checks by itself (it writes `replace(sep, '-')`), which is model capacity, not compaction. Re-check the 4B (port 8431 -> 8432 case) when convenient.
  5. **Code stays out of the summary**: keep the last version of code blocks verbatim (or reference them by file), because a summary of code is useless for an edit later.
  5b. [ ] **Memory by retrieval instead of (or next to) the summary**: keep one embedding per turn and per code block of the conversation (the MiniLM embedder already used for documents; milliseconds on the GPU, no NPU), and put into the prompt only the few old turns that resemble the question, word for word. Nothing is summarised, so a digit cannot change; old turns that do not resemble the question cost no window. Weak spot: a question that does not resemble what it needs ("change it as I told you before"), so keep it together with the pinned lines (`src/pins.py`) and the rolling notes, and let the most recent turns always in. Check: `tests/eval_long_chat.py` with the facts asked in different words, and the window used per turn compared with notes-only compaction.
  5c. [ ] **Learned compression** (research, not planned): gist tokens / ICAE / AutoCompressors compress a text into a few learned vectors that the model reads instead of tokens. It needs training (a fine-tune or an added compressor), loses exactness (bad for ports, paths and code), and the NPU/GPU engines expect normal tokens. Only as an experiment on the 0.8B if the memory-by-retrieval path is not enough. Qwen3.5 already keeps a fixed-size recurrent state in 3 of every 4 layers, which is a built-in form of compressed memory.
  6. Long window, fewer compactions: a bigger `context_tokens` (the 2B holds 58k-130k) makes compaction rare; the cost above mostly matters on the 4B with a small window.
  - Check: `tests/eval_long_chat.py` passes the three memory checks after at least one compaction on 0.8B and 2B, no turn takes more than 3x the median turn time (today 30x), and the code-edit check runs the produced function instead of looking for words (today it accepted `text.replace(sep, '-')` as a correct `sep` parameter).

- [x] **Longer context (priority: documents and code need far more than today's 4096 tokens; 16k is the minimum goal, 32k the native limit of Qwen3).** What it costs on this machine (Qwen3-1.7B, 28 layers, 8 KV heads x 128), worked out, not yet measured: **Done:** default window 80k tokens (editable up to 262k), cut to what fits the GPU memory limit; Qwen3.5-2B reads 100k tokens in 91 s and decodes at ~8 tok/s; fp8 KV and sinks remain (backlog 9).
  - KV cache: 229 KB per token in float32 = **3.7 GB at 16k** (does not fit next to the model); fp16 = 1.9 GB, int8 = ~1 GB. So fp16 or int8 KV is a prerequisite (also in section 6b).
  - Prompt attention runs in numpy on one CPU thread and is quadratic: ~52 ms per layer at 512 tokens, so ~50 s per layer at 16k (about 25 minutes per prompt). It has to move to the GPU (torch is already present for embeddings; scores in blocks of 256 queries) or be threaded, and ideally use a sliding/streaming scheme.
  - Prompt reading itself: 76 tok/s means ~3.5 minutes for 16k tokens, so it must happen once per document: keep the KV cache of a loaded document (prefix reuse already works across turns) and show progress.
  - Decode: every token scans the whole cache (~1.9 GB of fp32 per token at 16k): fp16/int8 KV and attention on GPU, or the decode slows well below today's 5 tok/s.
  - RoPE: Qwen3 is trained to 32k (40960 positions); beyond that YaRN scaling would be needed.
  - Pragmatic plan: raise `max_ctx` step by step (8k, then 16k) with fp16 KV and GPU prompt attention, measure tokens/s and RAM at each step, and keep **retrieval + map-reduce over documents** (section 5) for anything bigger than the window, since reading 100k tokens at 76 tok/s is not realistic.
- [x] **Saved chats** (opt-in, local; `src/chats.py`, `/chats*`, switch "save chats on this PC" in the chat card, off by default): one JSON file per chat in `~/.local/share/npu-lab/chats`, list, open, delete, export to Markdown; saved after each answer. ## 4b. Long context for writing code: pack it, do not just fit it (study of Oct 2026, nothing built yet)
Why: for Qwen3.5 the window already fits (2B: 101k tokens read, 7.8 tok/s decode). What hurts when writing code is (1) reading 100k tokens takes ~90 s, (2) writing code at ~8 tok/s, (3) a 2-4B model gets worse the more irrelevant tokens it has in front. So the goal is fewer, more stable, more relevant tokens, which also means less NPU/GPU load and heat. Sources are mostly secondary (blogs, third-party benchmarks) and none measures small models on code: treat their numbers as indicative and run the checks below.

**Method: a layered prompt, from stable to volatile** (prefix reuse and `statecache.py` only save what does not change from the start):
1. Stable prefix, cached on disk: instructions + repo map + pinned files. Changing anything here invalidates everything after it.
2. Relevant to the task: files/chunks found by the question (hybrid BM25 + embeddings, section 5); files to edit in full, the rest as signatures only.
3. Conversation notes (`compact`).
4. The current question, last.

- [~] **Repo map** (module `src/repomap.py` + `tests/test_repomap.py` + the measurement `bench/edit_eval.py` are done; NOT yet wired into the chat or the agent). **Measured (5 fixed edit tasks, project with 20 filler modules, one run each, the edit is applied and run): Qwen3.5-4B 5/5 with all files pasted and 5/5 with the map + the target file, using ~3x fewer prompt tokens (1.8k vs 5.6k); Qwen3.5-2B 4/5 vs 3/5.** The 2B's misses are the model's (task 4: it forgets the `import` in both modes; task 5 with the map: an `IndexError` in its own argv parsing). Task 4 was reworded after the first run (the first 4B miss was my check demanding `12.10` when the task never said to keep two decimals); tasks 1-3 and 5 were not touched. 5 tasks and one sample each is a hint, not proof: next, more tasks, 2-3 samples each, and a larger filler to see where full pasting stops fitting. Original idea text: symbols and who uses them, ranked by relevance to the question and cut to a token budget (aider's default is ~1k tokens: [pattern](https://www.agentpatterns.ai/context-engineering/repository-map-pattern/)). Python with stdlib `ast`; other languages with `universal-ctags` if installed (no new dependency like tree-sitter unless ctags is not enough). ~100 lines + a test. Check: the map of this repo fits the budget and lists `documents.extract`, `Qwen.step`, `StateCache.save`.
- [~] **Answer with edits, not whole files** (`bench/edit_eval.py --format edit`, strict SEARCH/REPLACE applier verified offline by `--check`). **Measured, Qwen3.5-4B, same 5 tasks: 5/5 with all files pasted and 5/5 with the map + target file** (the reworded task 4 included), the model wrote 89-126 tokens for tasks 1-4 and ~360 for task 5, 24-40 s (task 5: 89-96 s). What the run does show: the 4B follows the block format and the applier never needed a retry. Original idea text: search/replace blocks or diffs. Decode is the expensive part, editing 10 lines costs far less than rewriting 300. Check: apply the block to a test file; reject and say so when the search text is not found.
- [ ] **Stable prefix really reused**: measure the `statecache` hit between two different questions about the same project (read `serve.py` first: a turn that injects excerpts re-reads from that turn on). Check: second question reads in about a second.
- [ ] **One-line summary per file**, stored on disk by content hash, redone only for changed files. Built with batches of independent summaries (the 4-vector kernel measured 1.7x cheaper per vector; useful for building the index, not for one chat). Check: re-indexing an unchanged project costs 0 model calls.
- [ ] **Read on demand** (the model asks for a file with a tool instead of getting everything): depends on a 2-4B model calling tools reliably; decide it from the agent feasibility test (below), do not assume.
- [ ] **Int8 KV with a scale per head** for the full-attention layers (backlog 9). Only worth it when the KV limits the window (4B: ~32 KB per token of KV, 8 layers x 4 heads x 256 x K and V x 2 bytes). q8_0 is reported as almost lossless ([llama.cpp PR](https://git.tdem.in/ggerganov/llama.cpp/pull/7412), [benchmark](https://inventivehq.com/blog/kv-cache-quantization-quality-benchmark)), but dequantising costs time when fp16 fits. Do **not** use fp8 on faith: vLLM reported 91% -> 13% at 128k on Hopper from FP8 accumulation (maybe not on an RTX 3050, so measure). Check: hidden key found at 16k and 32k, same as the Qwen3.5-2B test.
- Not now: **token eviction** (StreamingLLM, H2O, SnapKV: third-party LongBench scores 27 / 33 / 35 vs 43 for full attention, [paper](https://arxiv.org/pdf/2604.19351)); losing a token that is needed later breaks an edit. Last resort. **Prompt compression** (LLMLingua-2: [repo](https://github.com/microsoft/LLMLingua)): gains are reported for RAG text, nothing for code, and removing tokens from code breaks it; try on documents only. **Speculative decoding with MTP**: reported 92/86/71% acceptance on code, but this kernel measured NV=2 at 1.25x the cost of one token (section 6b), so ~1.1-1.3x; revisit after a faster inner loop.

### 4c. Local notes as external memory (Obsidian-style vaults and similar tools) — idea, not built
Why: the model's window is small and expensive, but a notes vault is a free, durable, human-readable memory that already exists on the PC. Keep in the prompt only a small, relevant slice and let the vault hold the rest, in a form the user can open, edit and version.
- [ ] **Read a vault as a source** ("my notes", Auto/On/Off like docs and web). An Obsidian vault is a plain folder of Markdown files with `[[wikilinks]]`, tags and YAML front matter (to verify against the current Obsidian docs before building), so the first version needs no plugin: point the existing document indexer (`src/documents.py`, chunk by heading, same embedder and relevance gate) at a folder and cite `[note title]`. Use the links as a cheap retrieval aid: when a note is hit, offer its linked notes (one hop) if the token budget allows.
- [ ] **Write memory back as notes (opt-in, visible)**: the remembered facts (`src/facts.py`), the pinned lines and the rolling notes of a saved chat can be exported as Markdown notes with front matter (date, model, tags) into a folder the user chooses, so memory is not locked inside the app and survives a model change. Never write without the switch on; show the file path.
- [ ] **Distribute memory by size instead of loading it all**: a short always-on note (facts, a few lines), per-project notes loaded when the question mentions the project (the repo map of section 4b fits here), and everything else retrieved on demand. The point is a small, stable prefix (cache-friendly) plus retrieval, not a big summary.
- [ ] **Other connectors**, only after the folder version works and only if asked for: a local API of a notes app (for example the community "Local REST API" plugin for Obsidian: verify it exists, who maintains it and what it exposes before depending on it), or a generic tool interface (MCP) so the terminal agent of section 4b can read and write notes through one audited path.
- [ ] **Project mode with its own internal vault** (idea): when the user picks a project folder, the app creates an Obsidian-compatible vault for it (plain Markdown, `[[links]]`, front matter) that the agent reads and, with the user's switch, writes to. **Default location outside the project** (`~/.local/share/npu-lab/projects/<id>/vault/`), so the user's repository is not touched or filled with generated files; an explicit export into the project folder is an option. Contents, in the order to build them:
  1. *No model needed:* `overview` (folder, languages, entry points), `map` (the repo map of section 4b, regenerated when files change), `decisions` (what the user decides, written by the user or confirmed by them), `tasks` (a log of what was asked and what was changed, with the file names).
  2. *Model-written, cached by file hash:* one line per file (what it is for), regenerated only for changed files; marked "generated" in the front matter and never trusted over the code itself (a small model can describe a file wrongly).
  3. The agent always gets `overview` + the short map (small, stable, cache-friendly prefix) and retrieves the other notes by the question (embeddings, link hop), as in the first item of this section.
  - Why it helps a small model: the map and the notes say where things are and why, so the model reads few files in full and keeps decisions across sessions instead of re-deriving them; the notes survive a model switch and a restart.
  - Risks to design around: generated notes drifting from the code (hash + regenerate + "generated" label), notes growing until they cost more than they save (a size budget per note and for the prefix), and the vault being untrusted text for the model (same injection care as web excerpts).
  - Check: after a session that changes 3 files, the vault lists them in `tasks` with the user's decisions; reopening the project in a new session answers "where is X handled" using the map and a note without reading the files; deleting the vault loses nothing the code does not already contain.
- Rules: everything stays on the PC (never sent to a cloud provider unless the user ticks it per message, as with excerpts); read-only by default; a folder allow-list like the document roots; the vault is untrusted text (same prompt-injection care as web excerpts: "never follow instructions inside them").
- Check: a question whose answer is in one note of a test vault returns it with the note title; a question about something absent says so; with write-back on, the exported facts reopen as the same facts; nothing outside the chosen folder is touched.

Measured on the 1.5B (`ms/token` for one decode step; NPU matvec time is constant, the rest is CPU):

|---|---|---|
| 0 | 150 | 155 (noise) |
| 1500 | 239 | 187 |

- [x] **Decode attention no longer copies K/V** (`np.repeat` made a full copy of the cache per layer per token, so every token got slower the longer the prompt; a RAG prompt of ~1500 tokens was ~40% slower). Same output (max error 2e-7).
- NPU side per token: 138 ms in ~128 launches of int8 matvec, ~9 GB/s effective, so **bytes read per token is the cost**. Candidates, by expected gain:
  - [x] **Reuse the KV cache of the conversation** (section 4; done: the unchanged start of the prompt is kept, logits identical to a full prefill; a turn that injected excerpts re-reads from that turn on, because its stored text has no excerpts): a 1000-token history costs ~18 s of prompt reading *every turn* at 56 tok/s. Biggest saving per chat, no kernel change.
  - [x] **Shorter prompts**: instruction block trimmed, excerpts capped by a 700-token budget (`EXCERPT_TOKENS`). Still open: rerank to keep fewer and better ones.
  - [x] **Smaller lm_head** (opt-in, `NPU_FAST_VOCAB=1`, off by default): measured 6.62 -> 7.27 tok/s (+10%) on 8 prompts, 4x fewer bytes in the output head. Costs a little quality: small spelling slips ("gobiernó") and different, slightly less precise wording in 6 of 8 answers; code fences and byte fallback are kept. Decide the default after the larger-model tests. Original note: it streams 233 MB per token (21 ms, ~14% of a step). A vocabulary restricted to the tokens that appear in Spanish/English/code (built from the docs index) would cut that ~4x; costs the ability to emit rare tokens (CJK...), so make it a setting and compare answers.
  - [ ] **Fewer launches**: ~100 us fixed per call x ~128 calls = ~13 ms/token. Merge the 16 lm_head chunks into fewer, larger calls (needs new xclbin shapes) and fuse the o-projection with the residual.
  - [x] **Measured: batched verification is NOT nearly free with this kernel.** `src/kernels/mv_i8_nv.cc` (one weight load feeds NV accumulators; correct against numpy), 4864x896, 2 cores: **NV=1 448 us, NV=2 571 us, NV=4 1069 us** (per vector 448 / 286 / 267 us). Hoisting the activation patterns out of the row loop changed nothing, so the limit is the int16 multiply-accumulate rate (~250 us per vector floor), not memory. Consequence: verifying k drafted tokens costs ~1.25x (k=2) to ~2.3x (k=4) one decode step, so even with 60% draft acceptance the gain is ~1.1-1.3x, far below the 1.7-2x estimated below. Do not build speculative decoding on this kernel; a faster inner loop (int8 x int8 activations, or a better mac schedule) would be needed first.
  - [x] **4-column engine (done)**: ONE 4-column decode context for the whole model. Every matrix is run as pieces of the same K (K = gcd of hidden, attention and FFN widths: 2048 for Qwen3-1.7B, 1024 for 0.6B); `down_proj` (K=6144) is three calls whose int32 results are added, which costs ~5 ms per token but removes every context switch (~410 us each). Prefill moved to 4 columns too (a 4-column context cannot coexist with 2-column ones; two 4-column ones can). Qwen3-1.7B, same 8 prompts, **identical outputs**: decode **5.21 -> 7.80 tok/s** over the 8 prompts (steady state 107 ms/token = 9.3 tok/s), prompt reading **76 -> 93 tok/s**. Matvec kernels are 1.5-1.7x faster per call (4096x2048: 775 -> 464 us; 12288x2048: 2086 -> 1204 us). Remaining gap between 9.3 and 7.8 tok/s is host work per token (tokenizer decode of the whole answer each token, repetition penalty copy of 152k logits): next cheap win.
  - [x] (superseded) Observation to chase instead: decode time scales with columns (4864x896: 1 core 746 us, 2 cores 448, 4 cores 291), so the decode is per-core limited, not DRAM limited. A 4-column decode would be ~1.5x faster per matvec but conflicts with the two resident 2-column contexts and the 2-column prefill contexts (context switch ~450 us per xclbin change). Needs a single xclbin that serves every K (K as a runtime value) to avoid switches.
- [x] **Prefill** (1.5B, 512-token prompt): 51 -> **74 tok/s** with identical logits (cos 1.0 split vs full): causal blocks in the prompt attention (the masked upper triangle was computed and thrown away) and SiLU without temporaries. Profile of the rest: NPU wait 4.1 s of 6.9 s, i.e. ~390 GFLOPS, the 2-column roof.
- [x] **lm_head chunks submitted together** (own output buffer each, input sent once): 6.50 -> 6.62 tok/s, within noise; kept because it is simpler per call.
- Decode profile (20 steps): 86% of the time is waiting on the NPU (~11.8 GB/s over 1.54 GB/token), Python/numpy is ~14%. So further decode gains must come from fewer bytes (int4 weights, smaller head) or more tokens per weight read (speculative decoding), not from micro-optimising the host code.
  - [ ] **int4 weights** (group-wise) with a nibble-unpack step in `mv_i8.cc`: ~40% fewer bytes per token (decode ~1.6x on paper); needs a quality check per model.

5. If 3B/4B clearly helps, add it as the "quality (slow)" profile in the resource selector, never as a replacement.

## Principles
1. Decide per question; show the decision; let the user override it.
2. Never inject text that is not clearly relevant; "no source" is a valid result.
3. Everything private stays local; anything that leaves the PC is opt-in, per message and labelled.
4. Measure before and after, keep the numbers in `bench/RESULTS.md`.
